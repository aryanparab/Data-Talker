02 — UNDER THE HOOD

A small pipeline.
A clear chain of evidence.

The model proposes a plan. The application validates and executes it. Each step has a specific job.

  1. 01

    Ground the question

    The live schema, foreign keys, metric definitions, and recent context go to the planner.

    CATALOG + CONTRACT
  2. 02

    Validate the SQL

    SQLGlot checks a single SELECT against allowed tables and functions. A rejected query gets one repair attempt.

    STRUCTURED PLAN
  3. 03

    Run with limits

    A separate worker opens DuckDB read-only, with external access disabled and time, memory, and output limits.

    BOUNDED EXECUTION
  4. 04

    Show the evidence

    Executed values become a table and a validated SVG chart. The SQL and assumptions stay visible.

    INSPECTABLE RESULT

A FEW THINGS TO KNOW
Can I connect my own database?

The public demo uses the preloaded synthetic dataset. It does not accept uploads or arbitrary database connections. The source separates catalog discovery, business definitions, and query execution so you can inspect how the system is built.

How reliable are the answers?

The app validates SQL structure and shows executed results, but AI can still choose the wrong calculation. Review the SQL and assumptions. The project includes offline safety and correctness tests plus an opt-in live regression evaluator; these are a small regression set, not a guarantee of general accuracy.

What happens to my questions?

Live questions, recent query context, and the synthetic catalog are sent to Groq. Recent question/SQL pairs stay in browser session storage until cleared or the session ends. Avoid entering sensitive information into this public demo.

Why might the demo take a moment?

The app runs on Render’s free tier and can sleep when idle. The first request may take longer to wake it up. Live questions also have request and model-call allowances; reviewed examples do not use model calls.
